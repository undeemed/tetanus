# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.

## Sharp edges

- **Names are settled.** The binary is `tetanus`; the publishable umbrella crate is `tetanus-hardness`, because bare `tetanus` is squatted on crates.io. Do not rename either.
- **Upstream disagrees with itself about `system-prompt/assemble`.** `architecture.md` puts prompt assembly before `agent/pre-step`; `agent-lifecycle.md` names the event and puts it inside the step. tetanus follows agent-lifecycle.md. The reasoning is in `docs/turn-flow.md` section 6.1; read it before "fixing" the order.
- **Four dispatch modes, not five.** Upstream's low-level API doc lists a `bail` mode; the harness primer documents four to plugin authors, and Phase ① implements those four. `bail` is reachable through serial.
- **The merge gate is the conformance suite.** `MOCK_TURN_FLOW` in `crates/turn/tests/harness/mod.rs` is the whole expected event sequence, asserted by equality. Changing the driver's event order means changing that constant on purpose, in the same commit, with a reason.
- **Every test runs offline.** No case may need an API key. The one live provider case reports itself skipped when `DEEPSEEK_API_KEY` is absent. Keep it that way, or CI stops being a gate.
- **One tracer, two readers.** `TurnTrace` (`crates/turn/src/trace.rs`) feeds both `tetanus run` and the conformance suite, so the printed sequence and the asserted sequence cannot drift. Do not add a second observer.
- **The engine<->presentation boundary is published, not implied.** `docs/interface-contract.md` is the spec; `crates/protocol` is the same contract as Rust types. Any change to either lands as its own PR touching both plus the doc's changelog, never inside a feature PR. The doc's file-ownership table says which lane owns which path.
- **`docs/contract-updates/` is how one lane says something to another.** The boundary doc is edited in place and every lane collides there, so a change or a question is written as its own note in that directory and folded in later. A note is the right answer to "I need something another lane owns" - never reach across and build it. **A note is not a delivery.** It is invisible until the branch lands, so anything another lane should act on now - a security finding above all - goes into the status line the hour it is written, with the note as the detail. `ui-terminal-send-secrets.md` sat unread for an hour because that was done in the wrong order.
- **Phase boundaries.** Layered config recompose, deeper reversible effects, the full tool pipeline, more adapters, a subcommand that hosts the WebSocket carrier, and the WASM host are Phase ②/③. `docs/PLAN.md` is the captain-approved decision doc. The JSON-RPC codec and both its carriers are served: `crates/rpc`, stdio and WebSocket, conformance in `crates/rpc/tests/`.
- **Docs are part of done.** `README.md` has a truthful status table, `ARCHITECTURE.md` is the workspace design description, `CONTRIBUTING.md` holds the dev commands. A behaviour change that leaves them stale is unfinished; `CONTRIBUTING.md` states the standards they follow.
- **There are two gates, and the second one is `sentrux gate`.** It reads the committed `.sentrux/baseline.json` and prints an absolute quality score: hold 7000+, floor 6200, and quote it in the pull request body. It scans `git ls-files`, so an uncommitted or untracked change is invisible to it: a new crate measures identically to `master` until it is committed. Commit the slice, then gate it, or the number is about somebody else's tree. **Never `sentrux gate --save`** - that overwrites the thing the branch is being measured against, so a branch that saves reports "no degradation" by construction. Where code goes moves the number more than what it does: registering one tool family in `crates/cli/src/main.rs` cost 432 points for forty-five lines and nothing at all in `crates/cli/src/tools.rs`, which is why the binary's tool composition lives there. `CONTRIBUTING.md` has the reasoning and the other two things that move it; refreshing the baseline is its own PR naming the commit measured.
- **A journal-payload case that asserts an explicit `null` must use `get`.** `serde_json` indexing answers `Value::Null` for a key that is absent, so `data["x"] == Value::Null` also passes on a record that dropped `x` entirely - which is the defect such an assertion exists to catch. `crates/turn/tests/upstream_retry_executor.rs` (TC-PORT-RETRYX-1) carries the form and the reason. The distinction is load-bearing here because the interface contract spends it: §4.3.2 payloads carry `null` for a fact that does not apply, §4.5 error `data` omits the key.
- **GitHub has two budgets and the fleet shares both.** `gh-axi pr view/list/checks` spend the *write* budget, which merges also need; `gh-axi api /repos/{owner}/{repo}/pulls/<n>` and `/commits/<sha>/check-runs` spend a separate read budget that is nearly untouched. That budget hit zero twice in one day and blocked merges that were otherwise ready, and a CI poll on a `sleep`-loop is what empties it. Read PR and check state through `gh-axi api`, once, when there is a reason to - never on a loop. `gh api rate_limit` reports the *untouched* budget, so it reads healthy at the moment the other one is empty; a `RATE_LIMITED` from `gh-axi` beside a healthy `rate_limit` is this, not a glitch.
- **Never delete a build cache to free disk; prune generations.** `python3 <firstmate>/data/tools/prune-cargo-gens.py $CARGO_TARGET_DIR 2` keeps the two newest generations per binary and holds the build lock, so a running compile waits instead of failing. Deleting a target dir buys a cold rebuild that reads as a wedge from outside, and hand-rolled pruning takes no lock and can delete an artifact a concurrent compile is writing. If pruning is not enough, ask the operator: the box is managed across lanes, not per lane. Run it *before* a gate rather than during one: pruning between cargo's build and its test-exec removes a binary cargo has already planned to run, and the suite dies with `could not execute process .../debug/deps/<name> ... (os error 2)`, which is harmless, fixed by re-running, and easy to misread as a test failure. A link that dies with `ld terminated with signal 7 [Bus error]` is the disk being full, not a code fault.
- **A shared `TMPDIR` means a shared file name.** Every lane exports `TMPDIR=/home/ubuntu/.cache/tmp`, so an obvious scratch path like `pr-body.md` is a path two lanes write. One PR here was opened carrying another lane's body text, written between this lane's `cat >` and its `pr create`. Use `mktemp` with a lane-specific prefix for anything a tool reads back, and check what actually landed - `gh-axi api /repos/{owner}/{repo}/pulls/<n> --jq .body` - rather than assuming the file you wrote is the file that was read.
- **A green test count is not proof the gate ran your code.** Confirm a case that exists only in your tree actually appears in the run - grepping the bare name unanchored, because a suite kept in an inline `#[cfg(test)] mod tests` prints `test tests::the_name`, so `^test the_name` reports a case missing that ran. Every lane must also point `CARGO_TARGET_DIR` at its *own* directory: cargo does not hash the final binary, every lane writes `debug/tetanus`, and the CLI tests exec that exact path through `env!("CARGO_BIN_EXE_tetanus")`, so two lanes sharing one target directory can run each other's binary and still pass.
- **A sleep that races the thing under test is a defect, not a tuning problem: fix the ordering.** Three cases went red this way in one day - a process-wide `MOCK_MODE` two cases both wrote, a `SIGINT` disposition inherited across `exec`, and a fake MCP server told to die on a one-millisecond timer. The last is the shape to recognise: `ReconnectPolicy::max_delay` is both the backoff ceiling *and* the uptime that buys a fresh budget, so a server sleeping 1ms inside a 20ms window is a 19ms margin between two clocks, and a loaded runtime that overshoots resets the budget every cycle until the case dies on its own five-second deadline. The fix was to hang up when the last handshake message had been answered - the same intent as an ordering, with no second timer to lose to (`crates/mcp/tests/harness/mod.rs::fake_server_dying_after_handshake`). Raising the timeout would have hidden it. **The direction matters when triaging**: a stall only breaks a case whose assertion needs *less* elapsed time than the threshold - the two remaining sleeps in that file both need *more*, so an overshoot strengthens them and neither is flaky.
- **The terminal-backed cases fail under load and pass alone.** `crates/ui/tests/killed.rs` TC-UI-TERM-5 and `crates/exec/tests/upstream_terminal_session.rs` both wait on a child arming itself or a signal landing, and a workspace run competing with other lanes' builds loses those races; each passes on its own and TC-UI-TERM-5 fails the same way on bare `master`. Several lanes have each spent a round proving it was not theirs. Before chasing one, re-run that suite alone, and if it still fails, run it from a scratch worktree of `master` - `tetanus-ui` depends on no workspace crate, so that build is cheap and the answer is decisive.
- **A note under `docs/parity-updates/` or `docs/contract-updates/` is the only copy of what it knows.** Both directories are empty on `master` as of 2026-08-22, because a reconciliation slice folded all 44 into `docs/parity.md` and `docs/interface-contract.md`. Keep writing them - a lane in flight cannot edit either shared document without colliding with every other lane - but a note that exists only on an unlanded branch is invisible: the UI crew's note that a `terminal_send` puts a password on the journal in plain text sat unread for an hour for exactly that reason. So **say in your status line, the same turn you write it, that the note exists and what it says**, and treat the fold as an event that happens later rather than as a queue somebody is watching. Folding is destructive - the notes are deleted - so whoever folds proves file by file that each one is folded or still present, and the proof runs against the master it will land on, not the one it started from.
- **`docs/parity-changelog.md` is generated; entries are one file each.** Write one with `python3 docs/tools/parity-changelog.py add "..."`, which drops a file in `docs/parity-changelog.d/` named with a hash of its text so two lanes cannot collide, and never edit the rendered table. This replaced a `merge=union` table: union merge works where the driver runs, but a merge driver is client-side configuration and the real problem was that eight of ten open pull requests were editing the same lines. Rendering (`parity-changelog.py build`) is a single-writer step on purpose - requiring it for a green build would make every pull request regenerate the file and recreate the shared line. Entries are historical facts: write one, never revise one, and a correction is a new entry saying what it corrects. Do not widen the pattern to `docs/parity.md` or `docs/interface-contract.md`, which are edited in place and where a conflict is information. **Rebasing a branch older than the split takes a specific order**, because the row sits *inside* the conflicted hunk and the correct resolution destroys it: note the pre-rebase head first, rebase, resolve `docs/parity-changelog.md` by taking the generated file, then `parity-changelog.py adopt --base <old-base> --head <pre-rebase-head>` to read the row from the commit that still has it. Adopting before the rebase does not work - those branches predate the tool. Done right the rendered file shows an empty diff and the branch carries only its entry file.
- **A compaction record and the event after it are one unit.** `compaction/summary` and `compaction/prune` name a range and price it; the *next* surface event replaces that range. Nothing may be appended between the two. It is not tidiness: it is what lets a projection price a replacement with one running total and one pending claim instead of a price per message, so a checkpoint stays bounded. `crates/turn/src/compaction.rs` produces the pair and `crates/turn/src/projections.rs` consumes it; break the adjacency and the totals drift silently.

- **Compaction lives in the derivation, never in the file.** The journal is append-only, so nothing is deleted to shrink a conversation - `compaction::surface` changes how history is *derived*, which is why a replay reproduces a compacted session. Anything that reads model history must go through `derive_messages`; a second reader that folds surface events itself will disagree with the engine the first time a session compacts.

- **A sandbox is proven by being denied, never by being asserted.** `crates/sandbox` restricts a real thread or a real child and then performs the operation, because a case that inspected a policy object would pass just as happily against a backend that never made a syscall. Two traps are already paid for: `tempfile::tempdir()` lands under `$TMPDIR`, which `workspace-write` grants on purpose, so "outside the workspace" needs a directory outside every grant; and the child's half between `fork` and `exec` must stay allocation-free, which is why the Landlock syscalls are made by hand rather than through the crate. `ARCHITECTURE.md` §4.10 is the description.
- **Leaving the process is `crates/exec`, and the switch has to be shared.** Every child is spawned as its own process-group leader and killed with a SIGTERM-to-SIGKILL ladder over that group; a tool that starts one reads the *turn's* `Interrupt`, handed in by the composition through `tetanus_turn::boot::boot_with`. `TurnEngine` mints its own only when nobody provides one, and `tetanus_engine` mints one per session on purpose - a switch shared across sessions would let an interrupt in one stop another. `ARCHITECTURE.md` §4.9 is the description.
- **A tool call is recorded before it runs, and a terminal journal is a credential store.** `Tool::recorded` is what the engine asks before appending, and it is asked in three places - `tool/call`, `assistant/message`, `assistant/chunk` - because the model said the argument too; a fix that covers only the first covers nothing. Failing closed here is *silence*: a redactor that panics withholds every argument, the opposite direction from `ToolMode`'s fail-closed, because a broken classifier costs concurrency and a broken redactor costs a credential. Behind the flag is one backstop and no more: a terminal whose last output line asked for a password withholds what is typed into it (`looks_like_a_password_prompt`, `sudo`'s mechanism for `sudo`'s reason). It composes with the flag by union, never override. `ECHO`-off and the `[wait: stdin_read]` sequence are both measured dead here - readline and `stty -echo` pin the first to a constant, and the second is the *ordinary* settle reason for every finished command - so do not reach for either.
- **Two persistent shell families, and they are not redundant.** `shell_*` (`crates/exec/src/session.rs`) is a shell reading a pipe: cheap, exact through per-command nonce markers, and ended whole by an interrupt because a pipe has nothing to interrupt. `terminal_*` (`crates/exec/src/terminal.rs`) is a shell on a pty: it runs what needs a terminal, and an interrupt costs the command rather than the session. A terminal send settles on the shell's own OSC 133 prompt marker, which is why it can report an exit status at all; silence and the deadline are fallbacks, and a send that settled on one of those left a command running whose prompt can settle the *next* send. Anything that changes when a send returns changes `wait_for_readiness` and the wait reasons together.
- **No host in this fleet has a PowerShell, and the CI runner does.** Every `pwsh` path is therefore unexercised locally and exercised on `ubuntu-latest`, which is how a terminal invocation that could never start on a pty (`-Command -` needs a *redirected* stdin; on a pty pwsh exits 64) stayed green here and red on every pull request. Assert a pwsh backend's argv rather than its behaviour, so the case fails on every host - TC-PORT-SHELL-21 is the form. To reproduce a pwsh-only failure, put a release tarball's `pwsh` on `PATH`; nothing else about the box has to change.
- **Two shapes of child, one seam each.** A command you wait for is `crates/exec/src/proc.rs`; a peer you talk to over pipes is `crates/exec/src/piped.rs`, and `crates/mcp` starts its servers through it. Do not spawn a child anywhere else: the seams give every child its own process group and end the group, which is the only reason a server's helpers die with the server. Output past a capture bound is kept whole by the *producer* (`Tail` opens a spill writer on the first overflow), because anything above the seam only ever sees a result whose beginning is already gone.
- **What the harness inherits, its children inherit - and that includes an ignored signal.** A `SIG_IGN` disposition and a blocked mask both survive `fork` *and* `exec`, and POSIX has a shell ignore `SIGINT` for anything it runs in the background, so a harness started with `&`, by systemd, by CI or by an orchestrator used to hand every shell it opened an interrupt nobody could deliver: `killpg` returned success, `terminal_signal` said "delivered", and the command slept on. `crates/exec/src/signals.rs` resets the ignorable signals and empties the mask between `fork` and `exec` for every child; do not add a spawn path that skips it. The cheap test for this whole class - it generalises past signals to limits, descriptors and the environment - is to run the same thing twice, once from an interactive shell and once with `&`, and compare. Any difference is inheritance. It presented for days as three load-flaky tests.
- **A process group is not a terminal session.** Job control puts every job an interactive shell starts in a group of its own, so `killpg` on the leader misses `sleep 60 &`. `crates/exec/src/pty.rs` sweeps by session id through `/proc` for that reason; a group kill alone is how a harness leaves a `sleep` behind for an hour.
- **The offline mock's chunk count is load-bearing.** `crates/turn/src/llm/mock.rs` streams three text pieces and one tool call per first step whichever tool it picks (`!` in the prompt asks for `shell`, anything else echoes), because `MOCK_TURN_FLOW` asserts the whole event sequence by equality. Change the pieces and the conformance constant changes with it, in the same commit.
- **Outside-world failures are failed tool calls, never turn failures.** `crates/mcp` and `crates/web` both carry a class or code on the failed result (`McpFault::class`, `WebFault::code`), which is what the model reads and what a journal is searched by. The seams are what makes them testable offline: an MCP server is a `Link` (`crates/mcp/src/link.rs`) and every HTTP request is an `HttpTransport` (`crates/web/src/http.rs`), so policy lives above the socket and no case opens one. Keep new outside-world code on that side of the line. `ARCHITECTURE.md` §4.11 is the description.
- **`crates/mcp` ships a real MCP server for its own suite.** `src/bin/fixture.rs` is behind the `fixture` feature, enabled for the test profile only by the crate's self dev-dependency in `crates/mcp/Cargo.toml`; that is what makes `env!("CARGO_BIN_EXE_tetanus-mcp-fixture")` resolve in tests while a published build ships no test double. Protocol cases use a channel pair (`memory::pair`) and process cases use the fixture - do not merge the two files.
- **A runaway program is stopped only because the evaluator agrees to be stopped.** Rust cannot terminate a thread, so `crates/coderuntime` owns its own small language and spends fuel per step, reading a stop flag as it goes; that is why the local backend does not embed a real interpreter, and why `live_workers()` counts a worker stuck in a host binding as live rather than reporting a comfortable zero. It reaches no file, socket or subprocess, so it needs no sandbox - a real-language backend would, and `docs/parity-updates/coderuntime-backends.md` names that dependency on the shell lane.
- **A preset is resolved once, at `session.create`, and lives in the session header.** `crates/engine/src/preset.rs` reads the roster; the id lands in `SessionHeader::preset`, a fork inherits it, and a later document edit never moves a composed session. A preset's tool subset is taken against the registry *that session* will run on, so it composes with `EngineConfig::session_tools` rather than replacing it. TC-PORT-PRESET-5 is the case that pins the first half; `ARCHITECTURE.md` §4.12 is the description.
- **Every surface that serves the contract builds its engine with `tools::served`.** `catalog.tools` is answered out of `EngineConfig::tools`, so a surface that passes a bare `booted` advertises the engine's offline minimum - one tool - to every client on it. That is not hypothetical: `tetanus serve --frontend` did exactly that while `tetanus serve` was correct, because the composition was written out at one call site instead of being a function both had to call. TC-CLI-CAT-12 (`crates/cli/tests/catalogue_agrees.rs`) asks every surface of one build and compares the answers to each other rather than to a number; a *new* surface still has to be added to it, which is the residual risk and the reason to add the line when you add the surface.
- **A tool crate is not offered by the binary until it is a line in `crates/toolset`.** `sources()` is the whole registration surface: one named source per crate, drained through `Source::registered` so no tool crate needs an accessor. The binary composes it for both the catalogue and each session's registry, which is why `tetanus tools` and what a turn dispatches cannot drift. `crates/engine` deliberately is *not* a call site - it has no session and would gain a dependency on every tool crate - so it keeps the `builtin` source's tools as its offline minimum, held there by TC-TOOLSET-2. A green workspace proves nothing here: every tool crate tests its own tools, and only `crates/cli/tests/toolset.rs`, `mcp_boot.rs` and `catalogue_agrees.rs` exec the binary and see what it actually offers. That gap has now appeared three times - the five tool crates, the MCP servers a document declares, then a whole carrier - so treat "the crate is complete and tested" and "the binary reaches it" as two separate claims needing two separate cases.
- **Four durable journals, one crash discipline.** The session log, the job store and the schedule store all follow the same rules, and a fifth should too: the newline is the commit, a record the writer never finished is dropped *and truncated from the file*, and a finished line that does not parse is refused naming its number. Where they differ is repair - a session closes a dangling turn, a job store closes live work as `Interrupted`, and a schedule store needs none because its state is its rule plus its dispatch history. Copy the discipline from `crates/core/src/jobs.rs`; do not invent a fifth variant of it.

- **Anything time-triggered takes its clock as an argument.** `crates/core/src/schedule.rs` reads no clock of its own, which is why its whole suite moves time instead of sleeping and why a restart is testable at all. A module that reaches for `SystemTime::now` internally cannot be tested without waiting, and every such test is a flake on a loaded box.

- **TC-ENG-4 and TC-RPC-12 belong to whichever call is reserved *now*.** Contract section 4.2's `Reserved` status is served by a default trait body on `Engine`; those two cases assert that a reserved call answers `NotImplemented`, is routed rather than unknown, and is not advertised. Serving a call *moves* them to the next reserved call rather than retiring them, and the RPC routing arm is added by hand, so the arm that gets forgotten is the one no case names.

- **libtest's progress line has no newline, so a test child's first line of output is not its own.** Under `RUST_TEST_THREADS=1` - which the fleet uses to share the machine - libtest writes `test <name> ... ` with no trailing newline before the case runs, so a child's first `println!` lands on the end of that header; at more than one thread the header is written afterwards and the child's line is alone. Two consequences, both already paid for. A *marker* the parent matches must match the end of the line, never the whole of it (`crates/ui/tests/killed.rs`). A child that speaks a *protocol* on stdout must write one newline before its first frame to close the header's line, and its reader must stay strict rather than learn to skip a prefix - a reader that tolerates leading junk cannot tell a test harness from a corrupted stream (`crates/acp/tests/upstream_acp_client.rs`).
- **The external contract surfaces are four crates, and only one of them is a carrier.** `crates/query` reads a journal as data (the fold that derives each event's turn and step, since section 4.3.1 puts them only on the structural events); `crates/sdk` is the typed in-process client plus `gateway`, the descriptor catalog that makes the request surface enumerable - the codec's `match` is not; `crates/acp` speaks the Agent Client Protocol as a `tetanus_rpc::FrameHandler`, riding the stdio carrier rather than bringing a second one. A bridge's characteristic failure is a wait that never ends, so every wait in `crates/acp/tests` carries a deadline; keep it that way.

## Working the shared box and the landing queue

These are not about the code. They are what a session on this machine gets wrong,
and each one cost the fleet real time before it was written down.

- **Verify the ref, not the command output.** `git add -A`, `git commit` and `git push <branch-name>` are all silent about which branch they acted on, and `git push <name>` pushes that *branch*, not your `HEAD`. Two incidents in one session: an `add -A` mid-conflict swallowed another PR's whole diff into a wip commit, and a push-by-name from a throwaway proof branch published an un-amended commit for two minutes while the local echo cheerfully printed the sha it *believed* it had sent. Check `git branch --show-current` before you stage, and after pushing confirm the remote sha equals the sha you intended - not the one `HEAD` happens to hold.
- **A zero-conflict rebase on a file your commit rewrites wholesale is the dangerous outcome, not the good one.** A merge driver, a generated file, or a wholesale rewrite can all absorb someone else's change without a conflict and without a trace. Probe the content: for every row/symbol/case the other side added, assert it is present in the result. Doing this caught three changelog entries a clean-looking rebase had stranded, and five closed-as-zombie pull requests whose content was verified present on master by test-function name rather than by branch name.
- **Reads and writes to GitHub share a budget that `gh api` does not.** `gh pr view`, `gh pr list`, `gh pr checks` and `gh pr create` go through GraphQL, which is the budget that runs out; `gh-axi api /repos/...` is REST and is not. Open a PR with `gh-axi api POST /repos/OWNER/REPO/pulls --field ...`. Do not poll in a loop - read once when there is a reason to.
- **Never delete a build cache to free disk; prune generations.** `python3 docs/tools/prune-cargo-gens.py $CARGO_TARGET_DIR 2` keeps the two newest artifact generations per target stem under `debug/deps` and deletes the rest, holding cargo's own `debug/.cargo-build-lock` while it works so a concurrent build waits instead of losing artifacts mid-link. Everything it removes is something cargo rebuilds keeps the two newest artifact generations per binary and holds the build lock, so a concurrent compile waits rather than fails. Run it immediately *before* every gate rather than after the disk fills. Deleting the whole target directory buys a cold rebuild that reads as a wedged lane from outside; one lane lost an hour to exactly that.
- **Dry-run a procedure on a throwaway copy before running it on the real branch.** Instructions get written from the clean case. Copying a queued branch into a scratch worktree and running the procedure there found two defects in a fleet-wide rebase instruction - one that silently discarded the entry it was meant to preserve - before it touched anything that mattered. A `git worktree add --detach` and a branch you delete afterwards costs minutes.
