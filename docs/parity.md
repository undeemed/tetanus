# Parity gaps against upstream

## 1. Identification

- **System:** tetanus (binary `tetanus`, umbrella crate `tetanus-hardness`), version 0.1.0.
- **Tracks:** deepseek-harness `0.1.0-rc.7`, commit `99f6f02fec`, consulted as a read-only reference.
- **Purpose:** name what upstream does that tetanus does not do yet, and the phase that closes each gap.
- **Status:** current as of 2026-08-22, when every lane's note was folded into this file. Section 6 records every change.
- **Authoritative copy:** this file, in the tetanus repository.

This is a gap list, not a design description and not a test plan.
Design lives in [../ARCHITECTURE.md](../ARCHITECTURE.md) and [turn-flow.md](turn-flow.md).
The engine/presentation boundary lives in [interface-contract.md](interface-contract.md).
The phase plan and the parity decision live in [PLAN.md](PLAN.md).

## 2. How the numbers were taken

Upstream spec files, counted in the reference clone:

```sh
find packages apps -name '*.spec.ts' -not -path '*/node_modules/*' | wc -l   # 650
find scripts -name '*.spec.ts' | wc -l                                       # 47
```

650 spec files across 49 package families, plus 47 specs that test upstream's own build and release tooling.
tetanus's own cases each carry a `TC-*` identifier and all of them run offline.
Their count moves with every merge, so it is not kept here as a number: it is what `grep -rhoE 'TC-[A-Z0-9-]+' crates/*/tests | sort -u | wc -l` prints.
Case counts are not a parity metric on their own: one upstream spec file can hold thirty assertions, and tetanus asserts a whole event sequence in one case.
They are used here only to size an area.

Parity is functional, not protocol-level ([../ARCHITECTURE.md](../ARCHITECTURE.md) section 6).
Upstream's web contract is generated from TypeScript decorators, so its client specs do not port one for one.

## 3. Areas

`Today` is what tetanus serves on `master`: a branch that is reviewed and not yet merged does not move a row.
`Closes in` is the phase from [PLAN.md](PLAN.md): ② is Cordis parity, ③ is the WASM host and the rest.

**One row per area.**
This table is a description and not a log, so an area that gained something is edited rather than appended to.
The rule is written down because breaking it is silent and cheap: appending is what a merge does by itself, and it once left 44 rows describing 28 areas, each spelling the same gap slightly differently, with three real clauses lost in rows nobody read to the end.

## 5. Deliberately out of scope

- **Upstream's unauthenticated web host.** `packages/host/webserver` performs no authentication and no origin check, and takes `'127.0.0.1' | '0.0.0.0'` as configuration, so any peer that reaches the port drives the harness. tetanus does not match this. A connection to `crates/rpc`'s WebSocket carrier can start turns, read every journal in the server's directory and read the resolved configuration, and the standing deployment rule is that served surfaces bind `0.0.0.0` for off-box access - so an unauthenticated port is a defect rather than a parity target. `tetanus_rpc::auth` requires a token from every non-loopback peer, checks `Origin` in every posture, and refuses before the upgrade; there is no posture that admits everyone. The one property its suite cannot pin is the constant-time token comparison: replacing it with `==` passes every case, because the difference is in how long a refusal takes rather than in what it answers, and a timing assertion would be flaky without proving anything.

- **`client/*` (125 specs).** Upstream's client is a web UI bound to a generated protocol. tetanus owns its surfaces and its UI is not a port of theirs, so these specs measure a product decision rather than a gap. tetanus does have a browser panel - `web/app`, served by `tetanus serve --frontend` - and it is built against the published contract rather than against upstream's components, which is why its cases carry `TC-HOST-*` and `TC-CLI-WEB-*` identifiers and appear in section 4 only where they port an upstream *host* package. The one thing genuinely ported from that family is the markdown renderer's refusals, because what a renderer will not do with untrusted text is a security property rather than a design preference.

- **JavaScript regexes, in the hook matcher.** Upstream compiles a hook matcher with `new RegExp`. `crates/hooks` uses the `regex` crate, which has no backreferences and no lookaround because it guarantees linear-time matching, so a pattern using either is valid upstream and refused here. This is a widening of what is refused, which is the safe direction: the failure a deployment cannot debug is a hook that was accepted and silently never fires. TC-HOOK-MATCH-11 pins the diagnostic and the matcher against each other so they cannot drift into that state, and adopting a JS-compatible engine later would only narrow the refusals, so nothing that works today would stop working.

- **UTF-16 units, in the recorded stderr summary.** Upstream caps a `hook/result` stderr summary with `String.prototype.slice`, which counts UTF-16 code units. `crates/hooks` counts characters, so a summary of astral-plane text is cut at a different point. Counting bytes would be worse than either - it panics mid-character, which is the defect the tool-result pruner's port already had to fix - so this counts what a reader would count. TC-HOOK-EVENT-11 pins it over two-byte, three-byte and surrogate-pair text.

- **How tools are composed.** Upstream loads a tool plugin through Cordis and resolves a duplicate name by load order. tetanus composes at build time from a declared set of named sources (`crates/toolset`), which is what makes duplicate detection possible at all - `read` is offered by `crates/fs` and may be offered by an MCP server, and the assembly refuses it naming both crates instead of silently swapping one tool's body under another's schema. A deployment's control is therefore over sources rather than over a plugin list.

- **`typert/*` (11 specs).** Type generation for that same protocol. `crates/protocol` is written by hand and tested by `crates/protocol/tests/wire.rs`.
- **`scripts/*` (47 specs).** Upstream's build, lint and release gates. tetanus has its own, in `.github/workflows` and [../CONTRIBUTING.md](../CONTRIBUTING.md).
- **`bundle/*`, `examples/*`, most of `test-support/*`.** Packaging and demos.

Out of scope means it does not gate parity.
It does not mean the capability is refused: if one of these turns into a real requirement, it arrives as a phase item in [PLAN.md](PLAN.md) first.
