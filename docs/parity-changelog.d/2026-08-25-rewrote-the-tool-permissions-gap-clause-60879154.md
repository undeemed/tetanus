Rewrote the tool-permissions gap clause, which described a surface upstream does not have and would have sent an implementer to build the wrong thing. It said a deployment must express policy by writing a Rust listener rather than by naming tools in the settings document, implying a per-tool permission table as the missing piece. There is no per-tool table upstream: its permission surface is an approval policy of ask-or-never plus a *preset* table bundling a sandbox mode with that policy, and `crates/fs/src/preset.rs` already serves the preset half with three presets, a `permission/preset` intent event and the same last-event-wins fold section 4.4.7 gives the policy itself. So the clause overstated the gap in one direction and missed it in another. What actually differs is narrow: upstream lets a deployment choose which preset a new session starts under from configuration and tetanus does not expose that, which is the real gap; and upstream lets a deployment define its own presets, which tetanus deliberately refuses with a reason recorded in that module - a preset naming knob values nothing checks is a misconfiguration a session discovers only when a tool is refused. The clause now says both, and marks which is missing and which is declined, because a gap column that cannot tell those apart invites someone to 'fix' a decision. Found by probing upstream for the table the clause described before building it; the search returned nothing, which is the answer that saved the work.
