The MCP servers a settings document declares are started by the shipped binary at boot (`tetanus_toolset::Servers`, TC-CLI-MCP-1..6), filling the last empty source in the assembly. `crates/mcp` could connect a server and bridge its tools from the day it landed and its own suite proved it did; nothing called it, so `mcp.servers.*` was a key the binary read and did nothing with. That is the third defect of this shape on a green workspace - five tool crates the binary did not offer, then this, then a carrier serving one tool while another served twenty-six - so it is recorded as a rule rather than an anecdote: "the crate is complete and tested" and "the binary reaches it" are two claims needing two cases. Three properties are asserted against the binary rather than argued. A server that will not start is named on stderr with its fault class and the run carries on, because a tool silently absent is a capability nobody took away. One connection per server per process is shared by every session, since an MCP tool belongs to its supervisor. And nothing outlives the command that started it: every surface runs the close-input, wait, kill ladder, and the cases read the process table to prove it. Landing this on top of `tools::served` rather than beside it meant the frontend carrier got declared servers without a line written for it, which is the payoff of that function and the reason the first cut of this slice - which wired four surfaces by hand and missed the fifth - was worth rebasing rather than re-applying.
