The tool table and the browser panel held to each other (`crates/toolset/tests/browser_views.rs`, TC-WEB-8..9). This crate promises that a tool crate which lands adds one entry here and changes nothing else in the workspace; that is true of the engine and false of the surfaces, because a tool added to `sources` is one the model can call and `tetanus tools` lists while the browser panel goes on drawing it as a JSON tree until somebody notices. Somebody noticing is how it had worked: diffing `tetanus tools` against the page's view table by hand found seven feature tools with no view weeks after they landed, and running that diff as a case immediately found two more nobody had looked at - `read_image` and `search`, both landed since the last pass. Accounted for means a view or a line in `STILL_BARE` giving the reason, and the list is asserted in both directions so it shrinks when the work is done rather than outliving it; a third case refuses a view for a name nothing registers, since dead code that reads as coverage is worse than a gap. The test lives beside `stock_registry` rather than in `crates/host`, where it would have meant a crate edge from the thing that serves files to the thing that knows about tools, added for one assertion. Reading the view tables needed care: scanning the files at large picks up the hook decision words `allow`, `deny` and `pass`, which look exactly like tool names, and a check counting those passes for the wrong reason.
