`session/load` served on both halves of the ACP bridge (TC-PORT-ACP-25..31), closing the last clause of the `acp/*`, `sdk/*`, `api/*` row that was buildable rather than blocked. A load is a paged read of the journal rendered through the same `updates_of` fold the live path uses, written as `session/update` frames *before* the empty answer ACP specifies - the replay is the whole product of the call, so a client told "done" before it had the history would have been told about work it cannot see. One `notify` function frames both producers on purpose: a client must not be able to tell a resumed session from a live one, and two framings of the same notification is the kind of difference that surfaces as a panel which renders live turns and not resumed ones. Nothing is stored to make it work, because the journal already is the history; and the session is registered on this connection only after the replay succeeded, so a failed load cannot leave a usable handle to a session that is not there, which TC-PORT-ACP-27 asserts by prompting after one. TC-PORT-ACP-30 is the claim worth having: a second agent *process* over the same journal root replays the first process's turn, so the conversation outlives the connection and the process both. Writing it caught a probe that had stopped being one - TC-PORT-ACP-16 proved that an unknown method is refused by calling `session/load`, which this slice serves, so it would have passed until it failed for an unrelated reason; it now probes with a method ACP does not define, the same trap `AGENTS.md` already names for TC-ENG-4 and TC-RPC-12. What is left in the row is now written as clauses naming their blockers rather than as a list: image and audio prompts wait on `tetanus_turn::llm::Message::content` carrying parts instead of a `String` - not on storage, which `crates/features` has had since the feature-tools slice, and the older note in `docs/parity-updates/acp-surfaces.md` claiming otherwise is corrected here; the permission channel is built and pinned on both sides but has no engine-side seam to be raised from, because `EventSink` carries two pushes and neither is a request the client answers, and adding one is a change to the published boundary rather than a line in this lane; `agent.steer` is still absent from `method::ALL` and stays a proposal against an engine-lane file; and session fork and list are not ACP gaps at all - the revision this bridge speaks has no call for either, the engine serves both and the SDK exposes them typed, so inventing `session/fork` here would be this bridge extending someone else's protocol.
