The fourth and last of the shared-resource races (crates/mcp/tests/harness/mod.rs, TC-PORT-MCP-23). ReconnectPolicy::max_delay is two things at once - the backoff ceiling, and the uptime past which the attempt budget resets - so a fake server told to die on a one-millisecond timer inside a twenty-millisecond stability window was a nineteen-millisecond margin between two clocks. A loaded runtime that overshoots makes every connection look stable, the budget resets on every cycle, the cap never empties, and the case dies on its own five-second deadline reporting that the crash loop was not stopped. Reproduced before changing anything by setting that sleep to 25ms, which fails identically and in 5.00s; CPU load alone does not reproduce it, because what decides the outcome is whether the timer beats the window rather than whether the box is busy, which is why it reads as load and is not. The fix says dies-at-once as an ordering: the server hangs up when it has answered tools/list, the last message of the handshake, and the channel hands the buffered answer over before the client sees end of stream, so the handshake completes and then the server is gone. There is no second timer to lose to. An earlier cut made a oneshot and dropped the sender, which resolves the receiver at once - the server then left before reading a byte and the handshake failed instead of succeeding and dying, the opposite failure; None and already-told are different states and the loop now says so. The two remaining sleeps in that file are deliberately untouched, and the triage rule is in AGENTS.md: a stall only breaks a case whose assertion needs less elapsed time than its threshold, and both of those need more, so an overshoot strengthens them.
