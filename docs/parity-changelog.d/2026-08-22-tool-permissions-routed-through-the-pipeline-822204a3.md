Tool permissions routed through the pipeline (`crates/turn/src/tools.rs`, `crates/turn/src/events.rs`, TC-PORT-INT-10..12), which is the dependency the `core/*` tool-permissions clause and the `hooks/*` `PreToolUse` deny both named. Before this the approval gate was consulted only when `ToolRegistry::permission` already returned `Ask`. That answer is static and written by the tool author, who cannot know a deployment's policy - so a gate reachable only for calls somebody had already flagged could never be *added* to an existing tool, which is exactly what a permission table and an out-of-process hook need to do. Every call now passes a `tools/permission` waterfall carrying the declared answer, and a listener may return a stricter one. Stricter only, and the fold enforces it rather than a convention: `Permission::most_restrictive` ranks `Allow` below `Ask` below `Deny`, because a listener able to widen could quietly un-gate the irreversible call a tool author deliberately gated, and the author is the one who knows it is irreversible. Ties keep the earlier answer's words, so a chain of policies reads in the order it ran. `Deny` is a new variant beside `Allow` and `Ask`, and the distinction from an `Ask` answered no is the point: a policy that already knows the answer must not stage a decision nobody is going to take, since there is no human in a hook's loop and the question would hang or fail closed on a decision already made - so a deny writes no `approval/asked` pair and the model reads the refuser's own words. The seam sits after `tools/pre-execute` and not before, which is the rule the gate already followed: a listener may rewrite the call, and deciding first would permit one command and execute another. `MOCK_TURN_FLOW` gains one line, on purpose and in this commit - the first draft put it before `tools/pre-execute` and the conformance suite caught that the code's order was the deliberate one. Three mutations, all caught.
