Fixed the reason a turn could not be stopped in any backgrounded deployment (`crates/exec/src/signals.rs`, TC-PORT-TERM-44). It had been visible for days as three tests that failed in the full workspace run and passed alone, which everyone including this lane first read as load. Load was a correlation: a busy machine is also a machine driven by a script rather than by hand. The cause is that a `SIG_IGN` disposition is inherited across `fork` *and* `exec`, and POSIX has a shell set `SIGINT` to `SIG_IGN` for anything it runs in the background - `tetanus serve &`, a systemd unit, a CI runner, an orchestrator - so the bash on the pseudo-terminal inherited the ignore and so did every command it ran. `killpg` kept returning success because delivery genuinely succeeded; the process simply ignored it, and `terminal_signal` answered "delivered SIGINT to foreground process group N" while `sleep 30` slept on. The diagnosis is two runs on one idle machine: from an interactive shell the sleep dies, with `&` it survives, reported delivered both times - which is why the fix is a disposition reset rather than a longer timeout. Every child of all four seams now starts with the ignorable signals at `SIG_DFL` and an empty mask, applied between `fork` and `exec` in syscalls only, as bash, sudo and tmux do at the same point; `SIGPIPE` is in the set because a Rust parent ignores it process-wide, which is right for this process and wrong for a shell. The case reproduces the cause rather than the correlation - it sets `SIGINT` to `SIG_IGN` in the test process and asserts the command still dies - and it bites: removing the fix fails it in 10.9s, restoring it passes in 0.3s. Two further defects fell out. An interrupt must reach the shell as well as the foreground group, because a shell running a list forks one job per iteration, so signalling the foreground kills one `sleep` and the shell starts the next - that case had been passing on an idle machine by accident, since idle timing catches the shell between jobs, which is the one case where the shell does get the signal and does abandon the list. And a send that did not settle on a prompt leaves the shell owing one, which could settle the next send instantly with an empty viewport, reporting a command that never ran as finished; the debt is counted now, replacing a bounded wait a busy machine won and removing a hazard the module had documented as unavoidable. Nothing was ignored, serialised or weakened: the two cases that asserted through the race now wait for the state they are about - the shell reclaiming the terminal, the output stopping - rather than for a fixed 400ms. The rule this leaves behind generalises past signals and is in `AGENTS.md`: what the harness inherits, its children inherit, and the cheap test for the whole class is to run the same thing twice, once interactively and once with `&`.
