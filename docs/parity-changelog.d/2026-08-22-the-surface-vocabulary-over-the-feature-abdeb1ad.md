The surface vocabulary over the feature state (`crates/features/src/view.rs`, TC-VIEW-1..10). Not a port: upstream's panels read a generated protocol client, so what there is to restate is the shape a surface reads through, and the tetanus seam that carries the same decision is a serde type folded from the journal. `SessionView` folds todos, goal, plan, feedback and attachments in one pass, because four public folds a caller composes are four chances to draw four panels from four different moments; `WorkspaceView` is separate because it is read from the disk and changes when the disk does, not when the session does. Three rules are pinned by cases rather than by prose. Every view says how far it folded (`as_of_seq`, -1 for an empty log), since a live panel receiving two folds out of order otherwise cannot tell which is newer and a stale one cannot say that it is stale. A view carries no bytes: an attachment is named, measured and content-addressed, and `view::attachment_path` says where the content is - base64 in a fold is a frame nobody can read, a log line nobody can grep and a memory spike on every subscriber, for a thumbnail the surface wants once. A view carries no presentation: markdown arrives exactly as the model wrote it, because the surface knows the width and the theme and a guess here is a guess every consumer has to undo. `null` and empty stay different everywhere they appear, which is what lets a panel tell "no plan yet" from "a plan the model emptied" and "this is a project" from "this is a directory". Two fields that wanted an enum - `todo.status`, `goal.phase` - are strings, so a value added later renders as itself instead of failing to parse the whole view. The cases assert the JSON and not the struct, because the field names are the contract and a rename would leave the struct compiling and every consumer broken. Nothing in `crates/protocol` changes: publishing these over the boundary is two calls, the structs in `protocol::types` and possibly a push, and `docs/contract-updates/features-ui-surfaces.md` section 3 names all three so the presentation lane can say what it needs before that is settled. Writing it removed a second copy of the attachment store's layout - `view::attachment_path` delegates to `attachment::object_path` rather than joining the id itself.
