A byte window under the text read and an image read over it (`crates/fs`, TC-PORT-FS-58..62), closing two clauses of the `fs/*` row. They are one piece of work rather than two: the reason `read` cannot serve a picture - it refuses anything that is not UTF-8, and anything past the text cap - is the reason the service needed `read_bytes` at all. The window seeks rather than reading and slicing, so a caller that wants a header pays for a header, and an offset past the end answers empty rather than failing, because a caller windowing through a file meets that boundary on its last read every time. `read` stays the tool a model calls, since a model reading raw bytes is a model spending its context on a hex dump. The picture never reaches the model: `read_image` answers an id, a media type, a size and dimensions, which is the interface contract's rule for a view applied one layer down - base64 in a tool result is a journal line nobody can read. The store is a seam rather than a dependency: `ImageSink` is one method in `crates/fs`, the composition supplies it over `crates/features`, and with no store composed the tool is still registered and says what is missing, because a tool that vanished tells a model nothing and its author nothing either.
