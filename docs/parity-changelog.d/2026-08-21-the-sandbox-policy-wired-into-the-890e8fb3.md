The sandbox policy wired into the filesystem service (`crates/fs/src/kernel.rs`, TC-PORT-SANDBOX-20..27), closing the follow-up the sandbox slice named and making "one policy, both seams" true rather than intended. The arrangement is not the obvious one and the reason is worth keeping: Landlock restricts a thread irreversibly, and the harness has to go on writing its journal and answering its socket, so the process's own threads cannot be restricted - what is confined is one worker thread that restricts itself before it accepts any work, and every file operation runs there. TC-PORT-SANDBOX-22 pins the consequence that makes it the right shape, by writing harness files while the file service is confined. The central proof is built so it cannot pass by accident: TC-PORT-SANDBOX-20 sets the fence deliberately WIDER than the policy, so `SandboxedFs` resolves the path and permits the mutation - this build's own check says yes - and only the kernel refuses; the same write through the same backend without the layer succeeds, which is what attributes the refusal to Landlock rather than to the fence. The class it lands in was already waiting in the fs lane's vocabulary: `FS_PERMISSION_DENIED` means the operating system refused, as against `FS_SANDBOX_DENIED`, which means this build decided, and a model can act on the difference. TC-PORT-SANDBOX-23 is the requirement behind both lanes - one `Policy` value cloned into the file service and the process executor, refusing the same path on both sides, which is the asymmetry upstream's `roots.ts` note exists to prevent. One worker means file operations are serial; that cost is taken knowingly, because a pool needs one restriction per thread, and widening it is its own slice. The approved-escalation retry remains a follow-up, and belongs with `tetanus_turn::approval` rather than inside either enforcement layer.
