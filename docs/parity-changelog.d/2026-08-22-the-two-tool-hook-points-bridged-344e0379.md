The two tool hook points bridged onto the pipeline (`crates/hooks/src/bridge.rs`, TC-HOOK-BRIDGE-1..10). Every other module in `crates/hooks` is pure - which hooks match, what is written to them, what they may write back, how answers combine - and none of it knows a turn is happening; this is the part that binds those decisions to `crates/turn`'s extension points. The design question worth recording is that `PreToolUse` has two jobs that land in different places: a hook may rewrite the call, which belongs at `tools/pre-execute` because that event's answer *is* the call that then runs, and it may forbid the call, which belongs at `tools/permission`, the only seam that can refuse one. Running the hooks at both points would be wrong twice over - a hook is a program with side effects, so a deployment's audit trail would double, and the two runs could disagree, leaving the call rewritten by one answer and judged by another. So they run once, at the rewrite point, and the merged answer is held by call id for the gate that immediately follows; the hold is taken exactly once, so a retried call reusing its id cannot be judged by a run that was about a different call, and a parallel group is safe because its calls have distinct ids. Absence is inert in both directions, which is the property that keeps the bridge from failing open: a bridge that did not run leaves the declared permission exactly as it was rather than reading as approval, and a hook that *permits* also leaves it alone, because "I permit this" is not "and nobody else may object" - letting it lower the declared answer would un-gate the irreversible call a tool author deliberately gated. `merge_hook_outputs` deliberately has no opinion about a rewrite, there being no such thing as a more restrictive one, so the bridge states the rule instead: the last hook to supply one wins, since hooks run in configuration order and a later entry overriding an earlier one is what every other layered configuration here does. `PostToolUse` contributes one message per hook rather than one joined blob, because the notes came from different programs and joining them would invent a single voice. One fix travelled with the slice: `run_hook`'s clock parameter was `&dyn Fn() -> u64`, neither `Send` nor `Sync`, so the runner could not be awaited inside a bus listener - the one caller it exists for - and the bound is now widened. Five mutations, all caught.
