The filesystem service, its tools, and the permission gates on the tool pipeline (`crates/fs`, TC-PORT-FS-1..50; `crates/turn/src/questions.rs` and the gate in `crates/turn/src/engine.rs`, TC-PORT-INT-1..28), opening the `fs/*` and `interaction/*` rows. Every failure is a class with a code and a sentence a model can act on, because an `io::Error` string makes each caller above the backend parse a message to learn whether the path was missing, the file was binary or the fence refused - and a message is not a contract. The two backends share one containment walk, the one `crates/turn/src/fs.rs` already carries, so fenced and unfenced differ only in which root a path is judged against; `danger-full-access` selects the unfenced backend rather than becoming a branch inside the fence whose job is to skip the fence, which is the one branch a mistake in would be silent. The read-before-write policy is the rule that a session may not overwrite what it has not read, and it is keyed per session because borrowed knowledge is the blind write the rule exists to stop. The gate sits after `tools/pre-execute` and before the dispatch, so what is decided is what would actually run: approving one call and executing another is the failure a gate exists to prevent. Headless was the case that had to work rather than the case to leave for later - with no answerer the ask settles `unavailable`, the call is refused, and both halves of the pair are on the journal, so an unattended run neither hangs nor grants and a reader can see what was asked. Where tetanus parts from upstream is the widest preset: upstream bundles the `never` policy with full access because there `never` means "do not prompt", while here it settles every ask `rejected`, so that bundle would make the widest preset refuse the calls the narrower one allows.
