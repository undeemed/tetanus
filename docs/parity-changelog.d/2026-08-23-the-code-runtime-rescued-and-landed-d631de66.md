The code runtime rescued and landed (`crates/coderuntime`, TC-PORT-CODERT-1..34, TC-CODE-SET-1..4), after the branch was finished, measured, and then left behind when master moved. Reported as sixteen commits, it was nine: the other seven were the mcp/web lane's, which the branch sat on top of and which landed separately under different SHAs, so the replay was `--onto` the nine rather than a re-litigation of another lane's work. Every line of Rust survived two days of drift unedited and all 47 cases pass, which is the part worth recording: the seams it depends on - the tool trait, the registry, the turn pipeline - did not move under it. What did move is composition. `crates/toolset` did not exist when this was written, and master's rule is that a tool crate is not offered by the binary until it is a line in that crate's `sources()`; so `run_code` is built, configured and tested, and the shipped binary does not offer it. That is not a five-line addition and the note says why: every existing source is independent - `Source::registered` drains a throwaway registry holding only its own crate's tools - while `run_code` exists precisely to call the *other* tools, so `settings::tool` needs an `Arc<ToolRegistry>` that does not exist until `Assembly::build` has already run. Wiring it needs a late source, built from the assembled registry rather than beside it, which changes where the duplicate check runs and what `tools.sources` can switch off, and belongs to the lane that owns `crates/toolset`. One claim was corrected rather than carried: the README row said the runtime is "turned on from the settings document", which today would have a deployment set a key and get no tool; it now says registered by whoever composes a registry, with the binary wiring named in the `Planned` column. `settings.rs` is kept exactly as it is, because it is the function that late source will call. `docs/parity-updates/coderuntime-rebase-drift.md` is the note.
