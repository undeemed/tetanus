The built-in feature tools implemented (`crates/features`, TC-PORT-TODO-1..11, TC-PORT-GOAL-1..12, TC-PORT-PLAN-1..7, TC-PORT-FEED-1..6, TC-PORT-SKILL-1..12, TC-PORT-WS-1..5, TC-PORT-ATTACH-1..10), opening the `skill/todo/goal/plan/feedback/attachment/workspace` row. Every one of them keeps its state in exactly one place, the append-only journal, so a fold over the log is the state and a replay reproduces it - a cache beside the journal is a second copy that can disagree with it, and each module ships the case that proves the reload. The todo list is replaced whole every call because a per-item protocol needs stable ids the model has to remember across steps, and it is cleared by the next turn rather than by the end of this one so a finished checklist stays readable where a person looks for it. A goal change names the revision it is changing: a model completing a goal it read three steps ago may be completing an objective nobody set, and compare-and-set turns that into "read it again" instead of a silent wrong answer. Plan mode changes the prompt and never the tool catalogue, because a tool that appears and disappears between steps leaves the model working out which world it is in. Skills follow the precedence rule `crates/config/src/preset.rs` already settled - earlier root wins, the loser recorded as shadowed, a broken candidate reported rather than skipped - and `disable-model-invocation` is checked at the call as well as in the catalogue, so a model that guessed a name does not get a skill a person runs deliberately. Attachments judge the whole batch before storing any of it, since a half-admitted batch leaves the turn seeing part of what was attached with nobody able to say which part is missing, and an image is measured from its header so the pixel limit lands before the decode that would cost the memory.
