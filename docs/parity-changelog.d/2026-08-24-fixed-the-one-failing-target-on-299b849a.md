Fixed the one failing target on master (`crates/turn/tests/upstream_lsp.rs`, TC-PORT-LSP-17), which three full workspace runs agreed on and CI never sees. It was not a timeout and not load: the fixture handed each mock language server its behaviour through `std::env::set_var("MOCK_MODE", ...)`, and cargo runs a file's cases in parallel threads of one process, so the variable belonged to all sixteen at once and whichever case wrote it last decided what every other case's server did - which is why a test asking for an empty answer read back "mock server refuses to start", a sentence only the `die-on-init` server says. The evidence that it is ordering rather than timing: default parallel failed 3/3 runs with two or three failures each, and `--test-threads=1` passed 16/16 three times running. The fix is the ordering guarantee rather than a longer wait: a mode is an argument on the server's own command line, so it belongs to one invocation and cannot be read by another. TC-PORT-LSP-17 names the property the whole file rests on - two servers started at once, one told to die and one told to answer, each behaving as it was told - and it is a stronger guard than the bug was a bug: with the environment variable reinstated it fails 3/3 *even alone*, because the two `workspace()` calls inside it clobber each other, so it bites on a four-core CI runner that would never lose the original interleaving. Two product defects found in the same file are filed rather than fixed here, since they belong to the lane that owns `crates/turn/src/lsp`: the client inherits this process's whole environment (no `env_clear`, no listed env - which is *why* the fixture needed a global), and it spawns outside the one process seam, with no process group and no signal reset, so a server that starts helpers leaks them exactly as `crates/mcp` did before it moved onto `tetanus_exec::piped`.
